=== 2. DOES ANY EXPORTED RELATION PIN THE ORDER? ===
(a) Nodup / length / cl.3: leave the k-th assignment free (cl.3 is a membership statement; it even allows a let-port name, since the drop-part contains the lets).
(b) slot→register clause (:752): regs[k] has a register statement with init = slots[k].init.  It relates regs[k] to slot k only through the INIT VALUE (and, for insts=[], the width): it distinguishes positions only when inits differ.  By itself it does not give regs[k] = ps[k].name (no relation to ps or machPorts is in it).
(c) semantic clause of MachinePreservesX (:817-830): quantifies over env0 satisfying `SourceInputs … bsIn` (input binders only) AND `env0 r = posEnc … (bsIn.length + i)` for regs[i]; the conclusion is about `fieldNexts … regs slots`.  It says what regs do; it does not relate regs[i] to the i-th slot PORT NAME of machPorts (the slot binders are not in SourceInputs bsIn).  Not an order equation.
(d) MachineTraceLBX / ComposedGW semantic parts: hypotheses of the same shape about regs and st0; conclusion about outputs.  They constrain m's behaviour for regs satisfying the init hypothesis; they do not state regs = ps.names.  (A behavioural argument that order is forced would be a new theorem about the producer's module, i.e. K0-class body facts; not exported.)
(e) Concrete M/Q numbers (slots.length, lets, binders): the MachineData `d` of topshare{M,Q} is run-derived (MachineData.ok, Tools/ShippingMachineAuto.lean:221 decides it); these Props are not stated by any theorem I found as constants (grep topshareM in Tests/Compiler: theorems about hierGate/hkid/ranA/runFacts, none of `slots.length`).  A length/Nodup/subset argument would pin the order only if lets = 0 ∧ slots.length ≤ 1 (cl.3 then gives regs ⊆ the n+lets last names; with lets>0 even n=1 leaves a let-port name possible).  I did NOT evaluate M/Q's slot/let counts (would need elaboration of the actual declarations): per-instance status = NOT DETERMINED here; no counterexample permutation was constructed for the concrete M/Q.
   Predicate-level statement: the exported clauses are all invariant under any permutation π of regs that preserves the slot inits (slots[π k].init = slots[k].init), except the semantic/init hypotheses, which are hypotheses ON regs, not constraints. So for M/Q whenever two slots share an init the exported facts do not distinguish their order (stated about the exported Props, not about the producer).
