## 1. Background (no prior knowledge assumed)
A "parametric" compile (`synthesizeCombinationalWithParameters`, Sparkle/Compiler/Elab.lean:8940) keeps chosen `Nat` arguments of a Lean hardware declaration as module parameters, so a port can have a width like `n + 1`. To use such a design with a fixed-width consumer, `Sparkle.IR.Specialize.specializeDesign` (Specialize.lean:145) substitutes concrete numbers (a "binding" θ) and returns `.error` when some width becomes invalid (underflow, division by zero, zero width, inverted slice). The guarantee has two different parts:

- **(a) behaviour when specialization succeeds** (`ParamTopShips`): if `specializeDesign` returns `.ok` at θ, the specialized module runs as the declaration instantiated at θ. Success is a HYPOTHESIS there. Nothing in this document changes (a).
- **(b) success itself** (`SpecSuccessAllPositive`): "for every legal binding with all values ≥ 1 (and a present top module), `specializeDesign` returns `.ok`".

## 3. What the investigation found (and what it did not)
1. **Code reading, not a run:** the translator can put a user-written `-`, `/`, `%` of a retained parameter into a width (Elab:658, 660-661, 675, 678-679), and `specializeDesign` has error branches for underflow, division/modulo by zero, a zero `.bitVectorDim` and an inverted `.sliceDim` (Type.lean:68-93, Specialize.lean:49-62, 87-88). A width such as `n - 1` at `n ↦ 1` evaluates to 0 by that reading and `specializeType` would throw. This is an example read off the code; it is not kernel evidence and not a claim about every declaration that contains `-`, `/` or `%` (some of those succeed for all positive θ, e.g. when a larger term dominates). No classification of whole declarations is asserted.
2. **New in rev5 — the production functions are `partial`:** `DimExpr.evaluate` (Type.lean:68), `specializeType` (Specialize.lean:56) and `specializeExpr` (:75) are `partial def`s; the Check log lists `specializeExpr` and `specializeType` as opaque constants (body not visible to the kernel). What this does and does not show: the Lean definitions of these functions are opaque, so a statement about their result on a concrete width cannot be derived by unfolding them. **With the derivation route used in this work, no proof of success or of failure of the production `specializeDesign` was supplied, for any declaration.** The opaque observation alone does not show that no other route exists; this survey did not find one (sources read: the files in §6). Within the route used here, T needs a link ("Layer B", freeze §13.2) between the production functions and a total model of them, and this survey did not find a supply path for that link.
3. A pure structural induction over a total model (Layer A) is writable, but it proves statements about the model, not about `specializeDesign`.
4. **Reach probe, a Lean-checked observation on the EXISTING compiler (rev4).** `Tests/Gen4/ParamReachProbe.lean` (new file; unchanged `synthesizeCombinationalWithParameters` with `W ↦ 8`, then unchanged `specializeDesign` at W ∈ {1,2,3,4,5,8,9,16}; output printed at build time, nothing stored in the tree; one observation per binding, not a proof). Built with `kjob lake build Tests.Gen4.ParamReachProbe` in the pod (exit 0, 226 jobs; a pod build, not a clean issue-linked build).
| declaration (output width) | compile (`W↦8`) | specializeDesign, W = 1,2,3,4,5,8,9,16 |
|---|---|---|
| `W / 2` (`pDivOut`) | ok, port `BitVec(W/2)` | **W=1: error** ("port 'out' specializes to zero width"); W≥2: ok |
| `W + 1` | ok | all ok |
| `(W+1) - 1` (input `W+1`) | ok; the translator normalises the port type to `W` | all ok |
| `((W+4)/2)` | ok | all ok (positive for every W ≥ 1) |
| `(W+8) - W` | ok; the type came out as `(W+1+…+1) - W` | all ok |
| `W - 1`, `W - 2` (out or in), `W % 4`, `min W 8` | **compile throws** `Unsupported symbolic hardware dimension '…'` (the `whnf` in `extractDimExprStep` unfolds the term to a `match`/`Decidable.rec` before the operator test; Elab.lean:632-640) | nothing to specialize |
Consequences, each limited to what was observed: (1) **T as stated is false for the existing compiler**: `pDivOut` is a reachable declaration with a positive legal binding (W=1) for which `specializeDesign` returns `.error`. So T cannot be proved as written; this does not depend on option 2. This is an observation on one declaration and one binding; the exact wording change of T is the user's matter (§4, new D3). (2) The `n - 1` example of §3.1 is NOT reachable in the form `BitVec (W - 1)` on this compiler (compile-time throw); this survey did not check other surface forms of subtraction (e.g. through `Nat.pred`, a `have`, a type-level `if`). (3) `W / 2` and similar (`/`, and by code reading `%` in forms that survive `whnf`) are reachable. (4) The failures observed are all of the zero-width kind (`requirePositive`); no underflow/division-by-zero/inverted-slice error was observed in this probe.

## 4. Decisions that are the user's (only these)
**D1. Is a bridge for the three `partial` functions acceptable, and in which form?**
| option | what it gives | effect | cost | risk / reversibility |
|---|---|---|---|---|
| 1. None now (default) | (a) as built/planned; Layer A on a model only; T stays an unproved target | no change to any shipped behaviour or file | none | reversible: nothing is committed to; every report must say T is not supplied |
| 2. Production edit: make `DimExpr.evaluate`, `specializeType`, `specializeExpr` total (structural recursion) with the same behaviour | **Availability only:** the unfolding equations of the three functions become usable, so the link between production and a total model (Layer B) can be proved. It does NOT by itself prove that specialization succeeds for all positive bindings; that needs a separate success condition per declaration class (see below) | users see no change if the edit is behaviour-preserving; it touches `Sparkle/IR/Type.lean` / `Specialize.lean` (production, currently forbidden for this work) | moderate (nested `List`/`mapM` recursion over `Expr` needs care); needs a CSim/backends regression run; the later success proofs are further cost | needs the user's approval of a production edit; reversible by git revert; data loss: none |
| 3. New trusted equation law (the model equals the production function) | same as 2 without editing production | adds a TRUSTED boundary to the guarantee: the guarantee then rests on the law | small | not approved today; weakens the meaning of the proof; reversible but every downstream statement would cite it |
| 4. Narrow T to a class (user wording change) | T becomes "for the `PosPlus` class" | the guarantee is smaller than the current target | none | NOT proposed by this work; only the user can narrow FG; reversible by restoring the wording |

**What option 2 would and would not give (kept apart):**
- **PosPlus-conditional result (reachable after option 2, plus work):** for the class `PosPlus` (the freeze's complete definition, §13), "all-positive legal θ ⇒ specialization succeeds" can be attempted: the equations from option 2 plus a structural induction over every expression, module, array, body and assertion, parameter lookup existence and slice order. This is a conditional result about that class only.
- **T as a whole (NOT given by option 2):** T quantifies over all declarations with all-positive legal θ. Option 2 does not establish it. Two separate obligations remain and are not started: (i) **a real-reachability counterexample search** — for instance a width such as `n - 1` at `n ↦ 1`, which by code reading evaluates to 0 and would make specialization fail — i.e. determine from actual translator output, not code reading, whether declarations that violate T are producible; (ii) **a mathematical check of the success condition** — state which declarations T is true for, and prove it. If (i) finds a reachable counterexample, T as written cannot hold and the wording of T is a user matter (not decided here); if not, (ii) is still needed.
- Therefore option 2 is **a necessary-looking step for proving anything about success on the route used here, not the unique or sufficient way to keep T**. Other routes (including ones this survey did not find) are not excluded.

Recommendation: **1 now** (no commitment, nothing is claimed beyond (a)). The reachability investigation (§3.4) and the Layer A check of success conditions run on the existing compiler and need no production edit; they have been done without option 2. **2 is worth choosing only if the user wants the production success statements (the PosPlus-conditional result, or any statement about `specializeDesign`) to be provable**; it gives equation availability for the three functions and nothing else. Not recommended: 3 (new TRUSTED boundary); 4 is not proposed (only the user can narrow FG).

**D3 (new, from §3.4). What should T say?** T as written (all positive legal θ ⇒ success) is contradicted by `pDivOut` at W=1 on the existing compiler. Options: (i) keep T as the target and record it as false for the existing compiler (no guarantee of this kind is claimed); (ii) replace it by a conditional form: success holds for θ in a region `R θ` or for declarations in a class; examples: PosPlus (excludes `/`) and Layer A shows the model-level condition; (iii) change the compiler so that such declarations are rejected at compile time or width 0 is allowed (production edit; not proposed). Cost: (i) none; (ii) wording change of the parametric part of FG (the user's decision, the existing FG (a) is untouched); (iii) production edit plus regressions. Recommendation: (ii), conditional on the user confirming the wording; reversible. If no decision: (a) stays the only parametric guarantee and no all-positive success statement is claimed.

**D2. Add G+ (conditional form) next to T?** Recommendation: **defer until D1 is decided**: any production-level statement of G+ needs the same bridge as T. If D1 = 1, G+ can only be stated about the model (and that is not a production result). Reversible; adding G+ never removes T.
