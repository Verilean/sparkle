# 判断資料: compiler の展開処理（MachRecUnfold）を全域化するときの「燃料切れ」の扱い

Issue: `sparkle-rt-pass-total`（親 `sparkle-gen5-dg-readertrace`）。根拠: `scripts/gen5/RT_PASS_TOTAL_SURVEY.md`（調査 rt34、7f6b7880）、`scripts/gen5/RT_INLINE_SURVEY.md` §1.4。
台帳: FG 103 / T1 54（この資料での増減なし）。

## 1. 何の話か（前提知識なしで）

* Sparkle の compiler は、ユーザーの関数を回路にする前に「インライン展開」をする（`userInliner`）。その中の一段 `MachRecUnfold.pass` は、
  リストや自然数のリテラルを引数にとる再帰関数（例: `List.foldl` 相当のユーザー関数）を、データが尽きるまで展開する。
* この処理は Lean の `partial def`（停止の証明なしの定義）で書かれている。Lean の論理からは中身が見えないので、
  「展開しても式が壊れない（未解決の穴や範囲外の変数が出ない）」という定理が証明できない。
* 一般定理（FG）の reader 段は、inline 展開を通る宣言についてこの性質を必要としている。今は inline 枝は未解消で、
  非 inline の宣言だけで証明が進んでいる（`shapeInputs_of_direct`）。
* 方針（ユーザー 2026-11-01）: 「Sparkle 自身の partial は全域にして証明する。停止が示せないものだけを明示的な仮定にする」。
  前回（rootFloat / machLiftScalarN / machBoolMap）は、挙動を変えずに全域にできた。

## 2. 調査で分かったこと

対象 6 定義のうち:

* `iota` / `reduceHead`（と `relevantClosure`）: 既に回数の上限を持っていて、**挙動を変えずに全域にできる**（試作でコンパイル確認）。
* `headBetaM` / `betaAll` / `listLit?` / `passM`: 停止の理由が「型が付いた項だから」「ユーザー関数がデータを 1 つずつ消費するから」にあり、
  Lean の `Expr` の型の上では停止しない入力が実際に作れる（例: `(fun x => x x) (fun x => x x)`、自分自身を呼ぶだけの展開定義。
  どちらも試作で 20 秒以上止まらないことを確認。production の compiler が実際のソースから作る入力ではない）。
  したがって全域にするには**回数の上限（燃料）を入れるしかない**。燃料を入れると、上限を超える入力で挙動が変わる。

## 3. 選択肢

| | 内容 | 利用者に見える影響 | 前提台帳 | コスト |
|---|---|---|---|---|
| **A（推奨）** | 4 定義に十分大きな燃料（例: 10^6 回）を入れ、燃料切れは**コンパイルエラー**（理由つきメッセージ）にする。残り 2 定義は挙動不変で全域化。その上で保存の定理を証明する | 展開が 10^6 段を超える入力だけ、今は（時間をかけて）成功するか止まらないものが、エラーで止まる。今のコーパスで出力が変わらないことを全件比較で確かめる。回路の出力・保証範囲は変わらない | 増えない（`PassPh` 不要） | compiler 変更 ~70 行、保存の証明 ~400〜700 行、コーパス比較 1 回 |
| B | compiler はそのまま。「`pass` は式を壊さない」を明示的な仮定 `PassPh` として置く | なし | FG +1 | 小 |
| C | 挙動不変で全域にできる 2 定義だけ全域化、残りは据え置き | なし | 増えない | 小。ただし inline 枝は解けないまま |
| （判断しない） | C と同じく inline 枝は未解消のまま、非 inline の宣言だけで進む | なし | — | — |

* **データ損失**: どの案もなし（compiler の出力ファイル以外を触らない）。
* **運用リスク**: A は燃料の値が小さすぎると正当なソースがエラーになる。10^6 は現実のソースより桁違いに大きいが、コーパス全件で確かめてから入れる。止まらない入力は今でも compiler が固まるので、A ではむしろ止まるようになる。
* **後から変えられるか**: A は燃料の値・エラーの扱いをいつでも変更・戻せる（コミットを戻せる）。B の仮定は後で A に置き換えて外せる。

## 4. 推奨と理由

**A**。理由:
1. ユーザー方針（自分たちの partial は全域にして証明）にそのまま沿い、新しい仮定を増やさない。
2. 挙動が変わるのは、今の compiler では固まるか極端に遅い入力だけで、回路の出力や保証範囲は変わらない。
3. ただし「成功するコンパイルの集合を（極端な入力で）狭める」ことになるので、ユーザー判断として出す（reviewer の条件: 成功集合の縮小はコーパス比較だけでは正当化しない）。

## 5. 判断しないとどうなるか

inline 展開を通る宣言は一般定理の reader 段で未解消のまま残る（C.RT-2 等の減算ができない）。
並行して進めている他の単位（rev21.1 の DomKeepF 実装、S1 の `Expr.replace` / `headBeta` の仮定の freeze）は止まらない。
