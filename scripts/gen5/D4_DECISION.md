# 判断資料 D4: FG の前提 C.CV-1（LetQuoteEq）の文が、実際に通る入力で偽になる件（2026-11-01）

Issue: sparkle-gd-w3check。根拠: scripts/gen5/GD_W3CHECK3.md（08623644、reviewer が計算反例の調査資料として範囲限定で承認）。台帳 FG 102 / T1 54。この資料は何も変更しない。

## 何が起きているか（前提知識なしで）
- コンパイラは `circuit do` の各 `let` の値を、読み取りの途中で記録する（記録値）。
- 後で、回路の本体から読み直した同じ値（読み直し値）と比べる。FG の前提 C.CV-1（`LetQuoteEq`）は「両者が Lean の値として等しい」と言っている。
- コンパイラは本体を作るとき `machCanonAp` で正規化する。この正規化は、`Signal.ap (Signal.map (fun a b => …) x) y` の中のラムダの変数名を `x1 x2` に付け替える。記録値は正規化の前に取られるので `a b` のままになる。
- Lean の `=` は変数名まで比べる。そのため、意味は同じでも C.CV-1 の文は偽になる。
- 実例: `let t := Signal.ap (Signal.map (fun a b => a == b) x) y` を含む回路 2 つ（w3 と、子モジュールに渡す変形）。`dataOfAt` は成功し、同じ実行の読み取り状態で j=0 が偽だった（計算で確認。Lean の反証定理ではない）。対照の `let t := x === y` では真。
- 既存の corpus 466 宣言には、この形の `let` は見つからなかった。

## 影響
- 生成される回路は正しい（変数名だけの違いで、意味は同じ）。利用者に見える出力の問題ではない。
- 問題は証明側。C.CV-1 を前提にした道（W3 の witness 証明、W6 の `rowC_of_reader` の `hq`）が、この形の入力では成り立たない前提に乗ることになる。受理済みの定理は壊れない（前提として置いているだけ。このような実行に適用した場合にだけ根拠がなくなる）。
- 止まる後続: sparkle-gd-w3check（W3）、ロードマップの W6（C.SM-6 の GenWF 供給）、C.CV-1 を払う道全体。W1・G0〜G2・G6・reader-trace は止まらない。

## 推奨と理由
選択肢 1。コンパイラを変えず、保証も縮めず、変わるのは前提の書き方だけ。意味の上では元の文と同じことを言っている（変数名の違いを吸収するだけ）。

## 判断しないとどうなるか
C.CV-1 は、実際に通る入力で偽になりうる未供給の前提として残る。W3 と W6 は条件付きのまま止まる。他の段は進められる。
