# B5 (`hfresh`, 出力名と instance 配線名の衝突) のユーザー判断資料（docs only）

Issue: `sparkle-audit-carrier`（親 `sparkle-ledger-shorten`、束 B-AUD、台帳 D.E-4 の B5）。
この文書は判断を求める資料であって、判断を先取りしない。この carrier freeze（`AUDIT_CARRIER_FREEZE.md`）は B5 の判断を待たずに進められる。B5 の判断が要るのは、後続の E-4 B5 の証明単位に入る時点。

## 1. 前提知識なしの説明
コンパイラは、親モジュールの中で子モジュールを呼ぶとき、配線を `inst{gi}_{子のモジュール名}` という名前で作る。親の出力ポートがたまたま同じ名前なら、配線名が衝突し得る。FG の `TopShips` を証明する途中の補題 `machineClosesAtA_of_memKids'` は、その衝突がないこと（B5: `∀ gi k, ∀ o ∈ outs, o.name ≠ s!"inst{gi}_{nameK k}"`）を仮定する。
データ側の行 `outHead` はより強く「出力名の先頭文字が `'i'` でない」を求める（`MemCalleeData.outHead`）。

## 2. この調査で分かったこと（「見つからなかった」は経路が見つからなかったという意味）
- 先頭 `'i'` の検査は、証明生成コマンド側（`Tools/ShippingNoPortsMemSeqCommand.lean:380`、`throwError`）にある。コンパイラ本体（`synthesizeCombinational`）の run 中の検査としては、この調査では見つからなかった。
- したがって、出力名が `i` で始まる設計がコンパイラを成功で通るか、通った場合に実際に配線が衝突するかは、この調査では確認していない。
- FG の結論は「コンパイラ run が成功した設計」についての文なので、成功する設計がこの条件に反し得るなら B5 は FG の前提として残る。

## 3. 選択肢（どれも私は選ばない）
| 案 | 内容 | 利用者への影響 | コスト・リスク | 可逆性 |
|---|---|---|---|---|
| (a) 範囲を狭める | FG を「出力名が `inst{gi}_…` と衝突しない設計」に限る | 該当名の設計は保証の外 | 範囲縮小に当たる（禁止事項。ユーザー承認が必要） | 後から広げられる |
| (b) コンパイラ側で拒否または改名 | 出力名の衝突を throwError する、または配線名を改名する | 該当設計はコンパイルに失敗する、または名前が変わる | 本番コンパイラの変更。FG 以外の証明・テストへの波及は未調査 | 後から戻せるが、利用者に見える挙動が変わる |
| (c) 衝突しないことを証明する | コンパイラの命名規則から B5 を導く | なし | 経路がこの調査では見つからなかった。成功するかは未確認 | 証明なので可逆 |
| (d) 前提として残す | B5 を FG の前提のまま維持 | 保証は B5 付き | FG の前提数が減らない | いつでも変えられる |

## 4. 推奨
まず (c) の可否を調べる（設計の出力名がどこで決まり、`inst{gi}_` 形が現れうるかを実コードで確認する調査単位）。(c) が成り立たないと分かってから (a)(b)(d) を判断する。理由: (a)(b) は範囲またはコンパイラの変更で、(c) の調査には承認が要らないため。

## 5. 判断しない場合
B5 は台帳上 FG の前提として残る（(d) と同じ）。B-AUD の他の行（E-1〜3, E-4 の B3/B4, E-5〜9）は B5 と独立に進められる。
