# 判断資料: 「子の design の module 名が互いに重ならない」という前提（E-4 の B4）が、子孫を共有する設計で成り立たない件

Issue: `sparkle-aud-ua4`（B-AUD U-A4/U-A5）。
根拠:
- `scripts/gen5/AUD_UA4_STUDY.md`（dabf13f9、reviewer が調査として受理）§3、§5
- 既存の分析 `docs/parallel/A-shared-descendant.md`、`Tools/ShippingCallsKidsS.lean` のヘッダ

台帳: FG 94 / T1 54。この資料では何も変えない。

## 1. 何の話か（前提知識なしで）

* 一般定理（FG）は、いくつかの前提の下で「コンパイルが成功した設計の出力は正しい」と言う。前提の 1 つ D.E-4 の中に **B4** がある。
* **B4 の中身**: 親が呼ぶ 2 つの異なる子について、それぞれの子が持ち込む module の名前の集合が互いに重ならない（`hdisjD`）。
* **問題**: 2 つの子が、同じ孫の module を共有していることがある。例: `mixDeep` は `mid2` と `midH` を呼び、どちらも `rcH` を使う（`Tests/Compiler/NoPortsMixDeepTest.lean:6`）。
  * このとき、両方の子の design に `rcH` が入る。そのため B4 は **偽** になる。
  * 名前の集合をどう選んでも逃げられない（scratch `b4_refuted`、AUD_UA4_STUDY §3）。
* 前提が偽の設計について、FG は **何も言わない**（空虚に成り立つだけ）。つまり今の FG の保証は、子孫を共有しない設計にしか実際には届いていない。
* この指摘は、既存の文書（`docs/parallel/A-shared-descendant.md`）にも以前からあった。
* B4 が本当に要るのは、「同じ名前の 2 つの module は同じもの」という事実のためだけである（A-shared-descendant §1。証明の中の 1 箇所で、矛盾の枝を閉じるために使う）。重ならないことは、その十分条件にすぎない。

## 2. どれくらいの設計に当たるか

**未測定**。小さな共通部品（加算器、レジスタなど）を複数の子から使う設計は珍しくない見込み。しかし corpus の中で子孫を共有する設計が何本あるかは数えていない。これはこの資料の弱点である。

## 4. 推奨

**まず (3) を行い、同時に corpus で子孫を共有する設計の本数を測る。多ければ (2) に進む。**

理由:
1. (3) は嘘を書かない最小の手で、すぐできる。今の保証の届く範囲を正しく伝える。
2. (2) は保証を広げる正しい方向だが、新しい前提の供給の当てがまだ無い（UA7C の `DescProv` と同じ種類の未供給部分）。
3. 測定は小さい計測で、(2) に投資する価値を数字で決められる。そちらに向かうかの判断も、回路として現実にどれだけ当たるかで決められる。
4. (1) は範囲を狭めるので勧めない（狭めるのはユーザー判断）。

## 5. 判断しないとどうなるか

FG は文の上では全設計について言っている。しかし子孫を共有する設計では、前提 B4 が偽なので何も保証しない。説明だけを読むと、保証が実際より広く見える。
