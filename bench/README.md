# Sparkle Benchmark Suite

Compares Sparkle JIT simulation against Verilator on LiteX PicoRV32 SoC designs.

## Quick Start

```bash
cd bench
./bench.sh            # all benchmarks (LiteX 1-core + 8-core parallel)
./bench.sh litex      # LiteX 1-core only (= gate/run.sh)
./bench.sh multicore  # 8-core parallel only
```

## Prerequisites

- **verilator** — `apt install verilator` or `nix-shell`
- **g++** with C++20 (`-std=c++20` for `std::barrier`)
- **lake** — Lean 4 build tool
- **python3**
- PicoRV32 is auto-fetched from GitHub if not cached

## Benchmarks

### 1. LiteX 1-Core (`./bench.sh litex`, `gate/run.sh`)

Single PicoRV32 core with UART, timer, SRAM, main RAM: a 1730-line SoC
generated by LiteX/Migen, running `gate/fw/litex_bench.hex`.  Both
simulators get the same RTL and firmware and are co-simulated before
anything is timed; the comparison that CI enforces is executed
instructions per cycle (see [gate/README.md](gate/README.md)).

```
| model          | instructions / cycle |
| JIT            | 3733.8               |
| Verilator      | 2542.5               |
wall clock, 10000000 cycles: JIT 6.2 M cyc/s, Verilator 9.2 M cyc/s
```

(2026-10-02, gcc 15.3, Verilator 5.052, one workstation.)

> **The figure that used to stand here — "Sparkle JIT 11.65 M cyc/s,
> 1.13x faster" — was not a measurement of a correct model.**  The ROM
> was empty, so PicoRV32 trapped on its first instruction and an idle SoC
> was timed; the generator of that day updated registers in place, which
> breaks non-blocking semantics; and the JIT model never took its reset
> and read 0 from both RAMs.  With those fixed the JIT is at about 0.68x
> of Verilator on this design.

### 2. Multi-Core Parallel (`./bench.sh multicore`)

8 PicoRV32 cores connected via shared bus.
Sparkle uses CDC lock-free multi-thread runner.

```
==========================================
  Multi-Core Benchmark (10000000 cycles)
==========================================
JIT 1-core:          11.57 M cyc/s
JIT 8-core seq:       1.46 M per-core cyc/s
JIT 8-core parallel:  5.07 M per-core cyc/s    ← 3.47x speedup
Verilator 8-core:     1.06 M cyc/s
==========================================
```

### 3. RV32I SoC

Sparkle-native RV32I SoC (smaller, simpler design).

## Results Summary

| Config | Sparkle JIT | Verilator | Ratio |
|--------|------------|-----------|-------|
| LiteX 1-core (firmware running, co-simulated) | 6.2M | 9.2M | 0.68x |
| LiteX 8-core sequential ¹ | 1.46M | 1.06M | 1.38x |
| LiteX 8-core parallel ¹ | 5.07M | 1.06M | 4.78x |
| RV32I SoC ¹ | 14.2M | 8.7M | 1.63x |
| Timer Oracle (proof skip) | **49 GHz** | — | **9,900x** |

¹ Not re-measured since 2026-03.  The LiteX rows were taken with an empty
ROM on a JIT model that had the defects listed above (and, for the
multi-core wrapper, RAMs whose byte-enable writes were dropped), so they
do not compare like with like; CI currently reports the RV32I SoC JIT
below Verilator.  Treat them as historical until they are redone the way
the single-core row was.

## How Multi-Thread Parallel Works

1. Each core gets its own `sim_core` C++ class instance
2. N threads run `sim_core::evalTick()` in parallel
3. Shared bus data exchanged via `std::atomic` after each batch
4. `std::barrier` synchronizes threads between batches
5. Batch size controls sync frequency (10K cycles = sweet spot)

```
Thread 0: [eval 10K cycles] → barrier → [exchange bus] → barrier → repeat
Thread 1: [eval 10K cycles] → barrier → [exchange bus] → barrier → repeat
...
Thread 7: [eval 10K cycles] → barrier → [exchange bus] → barrier → repeat
```

## CI Integration

These benchmarks run automatically on GitHub Actions (push to feature/*):
- `dev/rv32-bench` — RV32I SoC tracking
- `dev/litex-bench` — LiteX 1-core tracking
- `dev/multicore-bench` — 8-core parallel tracking
