# VED 本番導入の要求と受入条件

2026-11-10。ユーザーの「既存IPで証明が通り、コンパイル時間・証明時間・回路規模が受け入れ可能な状態でリリースする」という要求を集約する。実装完了や測定結果の受理を宣言する文書ではない。管理先は `sparkle-ved`、リリース判定は `sparkle-ved-release-gate`。

## 1. 目的と完了の意味

一般コンパイラ健全性証明（FG）は保留し、既存の回路記述をコンパイルした**実際の成果物に、その元ソースとの意味の対応を示す証明を付ける**ことを優先する。

必要なのは任意の Lean プログラムへの対応ではなく、必要IPとして固定した回路記述への対応である。有限な map/list 等を展開してから証明してよい。無制限なリストや汎用高階関数をハードウェアとして実装することは要求しない。

小例の成功、一般補題の追加、CI成功、PRのmain導入は中間成果である。それだけでは本要求の達成にならない。必要IPが通らない理由を新しい前提に移しただけの成果も、受入成功には数えない。

## 2. 対象を減らして達成扱いにしない

- 固定対象は必要IPの inventory **327コマンド／136ファイル**。shipping IP 225、回帰102。基準 inventory は `par/fgc-s0` の `scripts/gen5/fgc_baseline/inventory.tsv`（固定版 f694355f、測定では完全SHA/blobを保存）。
- private宣言、元の引数、名前空間、open、scoped optionを尊重する。元の宣言を証明しやすい別宣言に書き換えて合格にしない。
- 複数出力、階層、メモリ、パラメータ等は、現在の入口で未対応なら未達として残す。分母から除かない。
- 目標は固定対象全体の対応。未達を残した限定リリースを提案する場合は、対象・保証・利用者への影響を示してユーザーの判断を受ける。内部判断で「対応対象だけ100%」へ変更しない。

## 3. 証明成功の条件

各行について、必要な全出力を満たしたときだけ行全体を成功に数える。

1. 証明の型に元宣言そのものと検査対象artifactを束縛する。入力・出力の型、幅、順序、projectionを照合する。
2. 検査するIRは、証明付き入口が同じ合成runから保持して返すIRとする。別の合成runのIRとの観測的一致だけでは代用しない。
3. 完全な期待型との照合、同期kernel受理、定理の存在、未解決変数がないこと、到達するaxiom閉包を確認する。strictの許可は `propext` / `Classical.choice` / `Quot.sound` のみ。
4. `native_decide`由来の非標準axiom、sorry、未供給の意味保存前提、証明省略、trace-only、rc=0だけを成功扱いしない。準備段階の定理がnative依存でも、最終証明の閉包に入らなければそのことだけで拒否しない。
5. 誤った出力値・初期値・幅・宣言・artifact・証明の取り違えを拒否する対照を持つ。検査に失敗した証明付き入口は成功結果を返さず、未検証経路への暗黙のfallbackを置かない。
6. 現行U1のorder-free契約では、適切に並べたbodyの存在と、対象となる全ての順序についての結論を維持する。存在しない実行順序についての空虚な成功を認めない。

## 4. 保証の段を混同しない

| 段 | 必要な対応 | 現時点での扱い |
|---|---|---|
| ソース | 元Lean宣言と深い構文表現の意味 | これだけでは返却IRの証明にならない |
| 返却IR | 元宣言と同じ入口が返したIRの意味 | U1 strictの計上対象 |
| 最適化IR | 返却IRから実際に印字する最適化IRへの意味保存 | 別の証明・検査が必要 |
| SV | 印字したSVの意味と検査済みIRの意味 | parse/roundtrip/文字列一致と意味保存を区別 |

U1の現行保証はreset=0、order-freeのIR意味についてであり、通常のCSim実行や最適化後SVまで自動的に保証するものではない。この範囲は中間段階として許可したもので、最終製品要求を縮小したものではない。リリース時にどの段まで保証できたかと残る境界を明示し、保証範囲の受入を確定する。

## 5. 利用者が使える入口にする

- 利用者が手で各回路の証明scriptやnamespace調整を作り込まなくても、サポートされたコマンドで証明生成・検査できることを本番化の到達点とする。
- 測定用 `u1_deep_ns` の成功は「名前空間補助付きの返却IR strict」として集計してよい。ただし通常の `u1_deep` の成功とは別列にし、元scopeで解決した完全な宣言名との一致を確認する。
- 通常二経路の和集合と補助経路を含む和集合を併記し、同じ行を重複計上しない。補助経路は本番入口へ修正または正式なwrapperとして接続するまで、通常の利用経路で対応済みとは呼ばない。
- 証明のために機能や回路を変える場合は、変更理由と機能・規模への影響をレビューする。未使用の出力や階層を落として証明しやすくすることは認めない。

## 6. 時間・資源・回路品質

同一候補SHA・toolchain・マシン・資源・設定で、コンパイル成功、証明成功、機能試験、成果物、時間、メモリ、回路規模を結び付ける。

- 合成、Deep準備、証明生成、elaboration/kernel検査、監査、全体wall、peak memoryを可能な範囲で分ける。分離できないものは合算と明記する。
- cold/warmを混ぜず、主要IPと外れ値は反復する。timeoutやsignalによる停止を単に「未対応」とまとめない。OOMは根拠がある場合だけ記録する。
- 既存の機能試験と出力比較を行う。回路規模はIRのregister/memory/instance等と、同じbackend条件のcell/LUT/FF/BRAM等を測り、SVの行数で代用しない。
- 許容する絶対時間・倍率・メモリ・回路規模の数値は未確定。実測から案を出しユーザーと確定する。数値を未決のまま「性能は許容範囲」と判定しない。
- 重い全量検査はrelease/定期gate、PRでは代表回帰を明示する。FG等の探索用証明を通常CIへ戻さない。

## 7. 報告と作業の区切り

進捗はファイル数や証明数ではなく、同じ基準に対する次の差分を最初に報告する。

- compile成功、返却IR strict、最適化IR/SVの各保証数（分母327）。
- 経路別と和集合、全出力成功と部分成功、通常入口と補助付き入口。
- 拒否の最初の段、後続未到達、残る原因、前回から成功へ変わった行。
- 時間・メモリ・規模の測定値と未測定項目。

入力/準備、生成器、kernelの拒否、非標準axiom、資源制限、harness不具合を区別する。生成器が未対応であることは、対応定理が偽であることや証明不可能であることを意味しない。

各実装単位は、狙うinventory行と未対応原因、一般化する規則、strictで通る代表例、拒否対照を先に決める。広い実装の前に最小縦断を確認し、通らなければ原因と次の選択肢を提示する。測定がまだ終わっていない群の件数を「増える成功数」と約束しない。

## 8. 現状と今回の反省

2026-11-10時点のcoder報告では、旧候補5df94720の固定対象はstrict 0/327であり、deep rc=0の13行もIR側にnative由来axiomが残っていた。mainのU1全量測定は進行中で、counterCdoのnamespace補助付きstrict成功がsmokeで報告された段階。全量結果・本番経路の受入を意味しない。

一般定理方式で問題だったopaque IO/runtime法則への依存とは別に、今回の障害には生成器の対応範囲、名前の受け渡し、非標準axiom、実artifactへの結合がある。方式を変えるだけでは、これらは自動的に解消しなかった。

限定例での証明成立と既存IPへの実用性を早期の同一測定で区別せず、後者を後回しにしたことを反省点として記録する。今後はこの文書の要求と327行の実測を基準とし、下位の実装都合で成功条件を変更しない。保証・対象・性能基準の変更は変更案として明示する。

FG台帳は75 / T1 57のまま。VEDの被覆・本番受入とFG台帳の減算は別に管理する。
