## 1. The recursion-depth failure of the probe's step 9

[M] `20261013-124156-sponge-grouped2`: `#machine_closes_deep keccak256SpongeHW`
FAILED after 42 s — "closes_deep was not generated: wKeccakF.iface_deep: the
generated proof fails: [maximum recursion depth has been reached …]".

**Where the option comes from** [R]:

* `Tools/ShippingChildIfaceGen.lean` 389–390: the command runs `closesDeep`
  under `withScope (fun s => { s with opts := Lean.Elab.async.set s.opts false })`
  — the AMBIENT options with `async` off. No `maxRecDepth`, no
  `withOptions`, no `withTheReader Core.Context`.
* The three generated theorems (`elabCommand` at 124, 245, 356) carry no
  `set_option`.
* Toolchain v4.32.1: a theorem's body is elaborated under `withOptions`
  (`Lean/Elab/MutualDef.lean` 1387, unconditional), and `CoreM`'s
  `withOptions` sets `maxRecDepth := maxRecDepth.get options`
  (`Lean/CoreM.lean` 288). The limit of a generated proof is therefore the
  SCOPE's option. The command `set_option maxRecDepth N` sets the scope's
  option and the command state's cached limit
  (`Lean/Elab/BuiltinCommand.lean` 519–520), which `runCore` hands to
  everything outside a declaration body (`Lean/Elab/Command.lean` 182).
* The probe's step 9 had `set_option maxHeartbeats 0 in` only: limit 512
  (the default). The BUILT uses have none either
  (`Tests/Compiler/ShippingCallsCloseDeepTest.lean` 26–33: `grand`,
  `grandH`, `mixD1`, `topD2` — small data).

So **the test can fix it**: `set_option maxRecDepth 1000000 in` before
`#machine_closes_deep` (the idiom of every built `#machine_no_ports_kids`
test, e.g. `NoPortsKidsMid2Test` 154). No change under `Tools/`.

**Which tactic** [I] — the probe's message is cut after its first line, so
this is not read off a log: `wKeccakF.iface_deep` is the theorem of
`ifaceDeep` 356–375: `kidsChild_of_real` (`Tools/ShippingKidsChildIface.lean`
357–385) with 14 `by decide` for its data hypotheses over
`wKeccakF.machineData` (124 binders, 27 slots, 69 lets, 27 outputs): `hC`
(`callsOk 27`), `hslots`, `hdomB` (∀ over the 97 binders after the first 27),
`hins`, `hsl`, `outTy` (27 outputs), `hkD`, `hIlen`, `hSL` (∀ over 96
binders), `hSlen`, `hLlen`, `hNIn`, `hnomem`, and the one inside `hselfT`.
`simp` over name lists and the `cases k` chain (ONE call entry) are not
candidates by size. Supporting measurement: the same facts are generated for
`wKeccakF` by `#machine_oneout` as `oneout_callsOk`, `oneout_slotLen`,
`oneout_domB`, `oneout_outTy`, … under `maxRecDepth 100000`, which THAT
generator sets in the scope itself (`Tools/ShippingOneOutGenCommand.lean`
217) — and they passed ([M] step 11 of the same run, OK in 19.6 s). Not
known: which of the 14.

**A fixed option the test can NOT lift** [R]: every theorem generated by
`#machine_no_ports_kids` is `set_option maxHeartbeats 4000000 in theorem …`
(`Tools/ShippingNoPortsKidsCommand.lean` 147, 332, 367, 395, 421, 446): the
ambient `maxHeartbeats 0` does not reach them. If step 5/6 fails with
"maximum number of heartbeats (4000000)", the minimal change is in the
generator: drop that line (the ambient option then applies, as in
`ShippingChildIfaceGen`) or read the ambient value and take the larger. Not
done here; a new-file variant would be a copy of the 700-line generator —
not small.

`first | decide | decide +kernel` (lines 389, 469, 471, 476) does not help
against a limit: a recursion-depth or heartbeat error is a runtime exception
and `first` does not catch it [I: from memory of Lean's `try … catch`
skipping runtime exceptions — NOT read in the toolchain source this round].
Under `maxRecDepth 1000000` the first `decide`
either closes the goal, fails normally (then the kernel variant runs), or
runs into the 4000000 heartbeats.

## 5. What a failure at each step would mean

1. data — the reading is wrong (class), a base constant of
   `OneOutWKeccakFTest` is missing (named), or a probe is co-imported.
2. endpoint — the base is not the probe's (its step 6: OK).
3. depth endpoint — not reproducible. The one difference from the measured
   run: `wKeccakF.machine_design_svHR` / `oneout_*` exist BEFORE it here
   (the probe generated them after). `KeccakProbeTest` had that order and
   reached the per-call loop [M].
4. `closes_deep` — with the same message: the option does not reach the
   generated proof (the reading of §1 is wrong). With another: the message
   names the theorem — `wKeccakF.iface_deep` (a decide that fails for a
   reason other than the limit), or `keccak256SpongeHW.closes_deep` (decides
   over 27 entries / 129 binders, the 27 arms). A process abort without a
   `FAILED` line: a stack overflow under the raised limit.
5. pieces — nothing; the lines localise step 6.
6. `#machine_no_ports_kids` — a refusal (scope: a constant of §2 missing); a
   failed decided condition (the message names the theorem); "maximum number
   of heartbeats (4000000)" (§1: the generator's own option); or the head /
   closed form not assembling (`dischargeWith`, the binder order
   `closedTerm` expects).
7. boundary close — "no conjunct … follows" (the boundary has another
   shape than `mid2`'s).
8. goal gap — the reporter cannot read the statement.
10. audit — in order: a generated lemma missing or on a non-standard axiom;
    a checker constant in a statement; the base NOT asking the four (the
    inventory is wrong); `MachineClosesAt` left in `_closed`; a binder that
    is neither the run nor a reflection (a name-separation premise `hN_…` —
    predicted none: the three names differ in the last component, outputs
    `d0…d3`, `done` do not start with `i`) or a count other than 4;
    `auditB`: more than `ChildBnd` kept (step 9 printed what), a NOT ALLOWED
    premise, a gap hypothesis.

1. Step 4 under `maxRecDepth 1000000`: a deep but finite recursion now runs

   fallback).
2. Step 5c / 6: the elaborator's `decide` on the 729- and 702-cell tables
   under the generator's fixed 4000000 heartbeats.
3. Memory: the grouped probe peaked at 1.72 GB (cgroup) WITHOUT the two test
