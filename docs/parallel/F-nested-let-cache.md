## 1. The change

`Sparkle/Compiler/Elab.lean`, `synthesizeCombinationalCoreWith` only
(+21 lines, nothing removed or moved):

* after `savedWireWidthCache`, three binds of the same shape:

      let savedLetWireCache ←
        if depth == 0 then pure ({} : Std.HashMap String String)
        else sparkleLetWireCache.get
      let savedLoopWireCache ← … sparkleLoopWireCache.get
      let savedWireCanon ← … sparkleWireCanon.get

* in the `finally`, inside the existing `if depth != 0 then`, after the two
  existing writes:

      sparkleLetWireCache.set savedLetWireCache
      sparkleLoopWireCache.set savedLoopWireCache
      sparkleWireCanon.set savedWireCanon

So at the end of a nested entry — returning or throwing — the five refs
keyed by wire names of the module being built hold what they held when the
nested entry started. At depth 0 nothing changes (three `pure {}`, no
write).

**Why only fvar and width were restored before.** No stated reason for
leaving the three out. The save / restore of `sparkleFvarValueMap` and of
`sparkleWireWidthCache` each carry a comment naming the bug they answer
(the width one is commit `8e79ecb6`: the parent read the child's width of
`_tmp_loop_0`). The `let` cache was added later (`f289c822`) by inserting
`sparkleLetWireCache.set {}` next to the existing clears in BOTH branches
of the depth test — the reset "per top-level synth alongside the other
caches" of its docstring — with no save / restore; the loop cache and the
alias map are cleared at the same two places, also without one (their
history was not traced). Nothing in the comments or the tests says the
parent is meant to continue on the child's entries.

**Does anything rely on the child's leftovers?** By the measurement
(`DTOP … MASK`, `docs/parallel/F-let-cache-leak.md`): the only observed
dependence is the defect itself (the `let` cache; the loop cache and the
alias map made no difference on `dTop`). By reading, a second dependence is
possible and is NOT a reliance: on poc a parent's own `let` entries written
BEFORE a child call are lost at the call, so a `let` re-walked after it is
translated again; with the fix it hits the parent's own entry and is
emitted as an alias of the first wire. That is the cache's documented
purpose (no duplicate hardware), but it CHANGES THE OUTPUT of any builder
that re-walks a `let` after a nested child was synthesised in the middle of
its walk — the legacy route, and the certified routes whose instance arm
calls the child entry (`translateInstanceOrFallback` → `childSynthEntry`).
Whether a measured declaration is such a builder is what §4 (c) is for.

**Unfixed by either.**

1. `sparkleSubInstanceOutputs` is keyed by the call's canonical hash and the
   field, with no module name, and persists across nested entries by design
   (the entry's comment); two of its three readers return the cached wire
   name without looking at the module being built. A child's entry can be
   taken by its parent after the child returns. Not exercised by any
   declaration here.
2. `sparkleSingleOutInstanceCache`: the legacy reader takes a hit without
   validating it (the certified arm validates).
3. `sparkleFvarZetaVisited`: cleared by no entry; a throw between insert and
   erase leaves a mark.
4. An exception: `keepWireRefsOnNone` does not restore on a throw (this
   fix's `finally` does run on a throw).
5. The stale-width question inside one builder (the `getWireWidth`
   candidate, separate).
6. The invariant below is CHECKED at the end of runs, not proved, and not
   observed at every point of a walk.

**The invariant.** "At every point of a module's legacy walk, the `let`
cache, the loop cache, the alias map (and the width cache) hold only
entries written while building THIS module by THIS builder." As a check
(`NestedLetCacheTest.orphansOf`, the `endOrphans` column; the `WIREREFS
LOCAL` idea): at the end of a run, every wire name these refs hold is
declared in the returned module. It is a necessary condition observed at
one point. Expected truth: on poc for `fTop` VIOLATED (the child's names,
e.g. the child's `_gen_k`); with this fix satisfied on the runs where no
machine arm ran in the parent (`cold`, `nofe`, `lPlain`); on a `real` run
of a fall-through it may still show the harness's names — that residue is
the rollback's.
